# TUI stream-CPU: layout-opt findings (2026-10-07)

## Measured baseline (lab, 400 items, sustained stream, headless pilot)
- Full reflows per streamed fragment cost ~55-80% CPU; key lag p50 ~2-4ms, spikes ~10-14ms.
- Band culling v5 (`/tmp/culllab5.py` subclass over TranscriptView): CPU ~35-54%, key lag p50 ~1.5-2.5ms, spikes <=7ms. Works but has scroll-position correctness issues (see below).

## The mechanism
- Every fragment -> `refresh(layout=True)` -> `_layout_widgets` non-empty ->
  `screen._refresh_layout` skips `reflow_visible` fast path -> full compositor
  reflow of all mounted widgets. O(mounted).
- `TRANSCRIPT_WINDOW_ITEMS = 200` in widgets.py:451, but real runs mount ~152;
  each ~8-row row costs ~7ms/reflow at 152 mounted.
- `visible=False` still lays out. `display=none` skips layout but collapses
  virtual size. Only way to pin virtual size while culling: override
  `get_content_height` to add `_band_above` (sum of estimated heights of
  unmounted items above the band) and translate coordinates in `scroll_to`.

## Working mechanics (validated in isolation)
- `scroll_to(y)` override translating absolute->band-relative works; all
  textual scrolling (wheel, page, scroll_end, scroll_to_widget) funnels
  through it. `scroll_to_widget` uses widget regions, so anchor restore after
  front-drop works unchanged.
- Height ledger: measure `region.height + margin.top` per item id after each
  relayout; GUESS=8 lines for never-measured items; recompute `_band_above`
  from the ledger (sum, never accumulate).
- Band ops: `_drop_front`, `_grow_front`, `_grow_end` (mount before
  `_bottom_boundary`), keep absolute viewport by remembering
  `keep_y = band_above + scroll_y` and restoring via `call_after_refresh`.
- vtune loop via `watch_scroll_y` + `call_after_refresh`, hysteresis BATCH=12.
- Window bookkeeping must trust only item-bearing rows; rows with `item=None`
  (streaming blocks) must be pinned at the band end, never dropped/counted.

## Remaining correctness issues (why not landed yet)
1. Follow mode: `_follow_output` is sticky True; any end-anchored branch snaps
   a mid-band view to the end. Guard needed: snap only when
   `_window_end >= total AND is_vertical_scroll_end` (at_band_end).
2. A jump-to-top (`scroll_to(y=0)`) clamped against `max_scroll_y` (band-
   relative) leaves scroll_y > 0 with ws==0 — clamp against
   `_band_above + max_scroll_y` instead, but growth chase then oscillates:
   band grows upward -> vtune re-drops because view sits mid-band.
3. Run-to-run nondeterminism: same script alternates snap-vs-chase; likely a
   race between after-refresh restores and vtune scheduling. Needs a single
   arbiter: one pending band op at a time, and vtune must re-read
   (band_above, scroll_y) atomically after every relayout.
4. `_request_follow_scroll` / anchor(True) interact with the band: anchor
   pins to virtual bottom, which is band end — fine while following, but
   `release_anchor` semantics on user scroll-up unchanged, ok.

## Cheaper alternatives worth trying before finishing band culling
- Reduce reflow cost instead of count:
  - Message rows have height that depends only on their own content + width.
    If the streaming fragment only changes one widget's height, the full
    reflow is still screen-wide — textual 8.2.8 offers no per-widget reflow.
  - BUT: rows are `Horizontal` containers with Static children; a reflow of
    N rows costs ~7ms at 152. If rows became `height: auto` Statics directly
    (no Horizontal wrapper) cost may drop constant-factor.
- Throttle: coalesce `refresh(layout=True)` during streaming to ~15-20Hz max
  (fragments arrive ~10ms; a 50ms coalescing window would cut reflows ~5x
  with invisible UX cost). This is a much smaller change: buffer fragments,
  refresh on a timer. CPU ~ proportional drop. Try this FIRST.
- Also: `screen.refresh()` repaint (strip diff) is separate; reflow dominates.
