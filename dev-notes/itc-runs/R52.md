**2. Why do the 254/255 boundary cases fail? Did cases.json include those examples, and how did a WITNESSED close pass?**

The defect is in encode, not decode. After a full block (code reaches 255), `codep = encode` is set without `encode += 1`. The C reference reserves the slot with `if (!*byte || length) ++encode;`. So the next data byte is written into the code slot and then overwritten by the next code. encode(01..FF) = `FF 01 … FE 02 00`: the `FF` data byte is lost. Every input with a run of 255 or more non-zero bytes loses one byte per full block. The 1000-byte cases are 3 bytes short.

How the defect got in:
- W4 (thinking off) wrote the C's continuation as `if byte == 0 or i < data_len - 1:` at W4 L42. It hit an IndexError at L45 and at L46 simplified the condition to `if byte == 0:`, which dropped the clause.
- The driver's T0003 notes (L33) had already described the same slot-less 255 branch. W4's IndexError fix fell back to it.

cases.json did not include those examples. It holds empty input and the reference's examples 1–4, all of 0–4 bytes. W1 read lines 61–120, which hold examples 5–11, including the 254/255-byte rows 7–11 ("9 | 01 02 03 ... FD FE FF" / "| 255 | FF 01 02 03 ... FD FE 02 FF 00"), and wrote none of them. Nothing in T0002's brief or close asks for the reference's other example rows. The source verdict even says that "a long sequence may be elided with `...` between its head and tail", so row 9 could have been sourced.

How the WITNESSED close passed:
- T0003's check was `pytest … -k encode` over the five short locked cases, and the defect does not touch inputs under 255 bytes.
- The witness, `if byte:` → `if not byte:`, proves only that the check catches that one mutation. "witnessed 3/3" says nothing about inputs the cases do not exercise.
