### [tau] Driver uses pursuit_dispatch in a founded pursuit, bypassing pursuit_step
Evidence: driver L21 and L83, two `pursuit_dispatch` calls; 0 `pursuit_step`;
T0002 is never opened; 45 of 58.6 min went into these two workers; the
plan result L20 had said "Next: pursuit_step." Prompt steering is ignored
(memory, run 4); only refusals change mimo's behaviour.
Action: in `examples/extensions/beagle.py::make_dispatch`, when not
`_is_worker()` and `_find_goal(cwd)` is set, refuse with "in a founded
pursuit use pursuit_step task=<ready id> …", naming the `next` ready task.
Alternatively, stop registering `pursuit_dispatch` beside the steering tools
(the registration block near line 4880, and the driver note at line 4345).
Regression test in tests/test_beagle_example_extension.py: in a tmp repo with
a founded pursuit, the driver's `pursuit_dispatch` returns the refusal, names
pursuit_step and the ready id, and spawns no worker; unfounded, it still runs.
